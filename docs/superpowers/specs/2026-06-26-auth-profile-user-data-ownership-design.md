# Separate auth & profile user data by ownership

**Date:** 2026-06-26
**Status:** Approved (design)
**Scope:** `authentication`, `profile` services
**Driver:** auth and profile both bind to the same MongoDB `users` collection and store
near-identical user records — a shared-database anti-pattern. Resolve by splitting the data
by bounded context, not by replicating-and-syncing.

---

## Problem

- Auth's user store is Mongo: `AuthUser` is `@Document("users")`.
- Profile's user store is Mongo: `Profile` is `@Document(collection = "users")`.
- Both map to the **same `users` collection**, with overlapping schemas
  (`username`, `password`, `authorities`, `firstName`, `lastName`, `address`,
  `phoneNumber`, `created`).
- Today the **profile service is the registration front door**
  (`/api/v1/profile/register-{user,admin,worker}`); it writes the shared collection.
  Auth's `UserService.loadUserByUsername` only **reads** that collection to issue tokens.
- Auth's Postgres currently holds only OAuth2 *client* registration tables — no users.

This couples two services to one collection and duplicates the same fields across two
bounded contexts.

## Decision summary

| Question | Decision |
|---|---|
| Ownership model | **Split by ownership, no sync** — share only `userId` |
| Registration flow | **Auth front door + Kafka choreography** |
| Auth credential store | **Postgres** (`user_credentials`, Flyway) |
| Existing data | **Clean cutover** — no backfill |
| Account deletion | **In scope** — auth front-door delete + `UserDeletedEvent` choreography |

---

## 1. Ownership boundary

One shared collection becomes two stores split by bounded context, linked only by an
immutable `userId` (UUID, generated by auth at registration):

| Concern | Owner | Store |
|---|---|---|
| Identity & credentials — `email`, `password_hash`, `roles`, `enabled` | **auth** | Postgres `user_credentials` |
| Personal data — `firstName`, `lastName`, `address`, `phoneNumber` | **profile** | Mongo `profiles` |

No field is duplicated except `userId`. Profile stores **no** password and **no**
authorities — it reads `email`/`roles` from the JWT, never from a DB. Nothing to sync.

## 2. Data model changes

### Auth
- Flyway `V4__create_user_credentials.sql`:
  - `id uuid PRIMARY KEY`
  - `email varchar UNIQUE NOT NULL`
  - `password_hash varchar NOT NULL`
  - `roles varchar NOT NULL` (or join table; comma-set acceptable to start)
  - `enabled boolean NOT NULL DEFAULT true`
  - audit columns: `created_at`, `updated_at`, `deleted_at` (per repo convention)
- New JPA entity `UserCredential` — `@Getter @Setter @NoArgsConstructor` (never `@Data`).
- New `UserCredentialRepository extends JpaRepository<UserCredential, UUID>`,
  `Optional<UserCredential> findByEmailAndDeletedAtIsNull(String email)`.
- **Delete** the Mongo `AuthUser` `@Document` and `AuthUserDao`.
- `UserService.loadUserByUsername` now reads Postgres via the new repository.

### Profile
- `Profile` document re-keyed by `userId` (`@Id` = userId string).
- Collection renamed `users` → `profiles`.
- Drop `password` and `grantedAuthorities` fields and the commented-out password code.

## 3. Registration flow (auth front door + choreography)

1. `POST /api/v1/auth/register` — validates, hashes the password, stores a credential row
   with a fresh `userId`, emits **`UserRegisteredEvent(userId, email, roles, firstName,
   lastName, phone, address)`** to topic `auth.user.registered`. Returns `201 { userId }`.
2. Profile consumes `auth.user.registered` (group `profile-group`, **idempotent on
   `userId`**, DLT `auth.user.registered.DLT` on failure) → creates the profile shell.
3. **Card/payment decoupled:** client calls `POST /api/v1/profile/payment-setup` with its
   JWT (`userId` from `sub`); profile runs the existing payment saga. Card data never
   touches auth or Kafka.
4. The three `register-{admin,worker,user}` endpoints collapse into one auth endpoint with
   a role parameter; profile-shell creation is role-agnostic.

## 4. Identity reads — no shared store

- JWT carries `sub = userId`, `email`, `roles`.
- Profile endpoints switch from username-keyed to **userId-keyed**
  (`authentication.name` = userId); `@PreAuthorize` expressions updated accordingly.
- `getUserByUsername` → `getByUserId`, reading the profile Mongo record and taking `email`
  from the token where needed.

## 5. Lifecycle flows that follow ownership

- **Password reset / set-new-password** move from profile (currently dead/commented) to
  **auth**, which owns credentials.

### Account deletion (auth front door + choreography)

Deletion mirrors registration: auth owns the lifecycle decision, profile and payment react.

1. `DELETE /api/v1/auth/account` — authenticated; `userId` resolved from the JWT `sub`
   (no path/query param, so a user can only delete their own account; an admin variant can
   accept a `userId` and be gated by `@PreAuthorize("hasRole('ADMIN')")`).
2. Auth **soft-deletes** the credential row: `deleted_at = now()`, `enabled = false`
   (never a hard `DELETE`, per repo convention), then emits
   **`UserDeletedEvent(userId, occurredAt)`** to topic `auth.user.deleted`. Returns `204`.
3. Profile consumes `auth.user.deleted` (group `profile-group`, **idempotent on `userId`**,
   DLT `auth.user.deleted.DLT` on failure):
   - soft-deletes the `profiles` record (`deletedAt = now()`);
   - runs the existing payment-customer cleanup saga (the current
     `deletePaymentCustomer(username)` logic, re-keyed by `userId`).
4. The existing `DELETE /api/v1/profile/delete-user` endpoint and `ProfileService.deleteUser`
   are removed — deletion is no longer initiated from profile. Profile only reacts to the
   event.

Ordering note: auth soft-deletes its own credential synchronously before publishing, so a
revoked account cannot re-authenticate even if the profile/payment cleanup lags. Profile and
payment cleanup are eventually consistent via the event.

## 6. Cutover (clean — no backfill)

1. Add `user_credentials` (Flyway `V4`).
2. Create the `profiles` collection; update `mongo-init`.
3. Drop the shared `users` collection.
4. Re-register test/seed users through the new flow; update seed data.

## 7. Testing

- **Auth IT** (Testcontainers Postgres + Kafka): register → asserts credential row written
  + `UserRegisteredEvent` emitted; login (`loadUserByUsername`) reads from Postgres.
- **Profile IT** (Testcontainers Mongo + Kafka): consumes `UserRegisteredEvent` → profile
  shell created; idempotent on redelivery; malformed event routed to DLT.
- **Auth deletion IT** (Testcontainers Postgres + Kafka): `DELETE /account` → credential
  soft-deleted (`deleted_at` set, `enabled = false`, not hard-deleted) + `UserDeletedEvent`
  emitted; a soft-deleted credential can no longer authenticate.
- **Profile deletion IT** (Testcontainers Mongo + Kafka): consumes `UserDeletedEvent` →
  profile record soft-deleted and payment cleanup invoked; idempotent on redelivery;
  malformed event routed to DLT.
- Coverage gate: 80% line / 100% on domain model (per repo convention).
